1 · Problem and contract

Keep dense RETRIEVE ownership through device completion

A shared L1 generation does not identify one request's reader share. FREE(A) followed by delayed completion(A) can decrement twice and consume B's protection in the same generation. Separately, read TTL may expire while an asynchronous transfer still uses the source allocation.

Session arbitrates original per-key shares between FREE and each (instance_id, worker_id). A transfer validates the original generation, pins resident buffers under a unique tag, and records immutable original ownership in its completion payload. Completion uses that receipt rather than live Session metadata and releases at most once. Publication failure synchronizes before release; failed synchronization keeps the pin. This refresh preserves upstream multi-L1 owner grouping and medium-specific managers; write fixtures pass explicit owners and fake clocks patch the new L1 base module. It does not introduce a different reclamation policy.

This is a correctness/lifetime fix. No model-quality, TTFT or throughput improvement is claimed. Fresh CPU and native CUDA evidence is distinguished from historical controls below.

2 · Before / after

Before · failure schedule

  1. A and B share generation
  2. FREE(A) decrements
  3. Completion(A) consumes B

After · ownership barrier

  1. Claim original share
  2. Pin source by tag
  3. Device completes
  4. Release receipt once

3 · End-to-end responsibility flow

  1. SessionOwn original per-key counts; partition them between FREE and worker claims.
  2. StorageManager / L1ManagerValidate original generations, route owners and retain buffers against normal reclamation.
  3. Transfer moduleSubmit copy with immutable owner/key/generation groups and a unique tag.
  4. Completion handlerRelease the original tag even if Session metadata disappeared; never consume a later generation.

The numbered sequence explains the intended protocol order, not a promise of serial execution across hosts. Failure handling and boundaries are stated below.

1 · 问题与契约

保持 dense RETRIEVE 所有权直至设备完成

共享 L1 generation 不能标识单个请求的读份额。FREE(A) 后再到 completion(A) 可能重复减计数，消耗同代 B 的保护；另外，异步传输仍使用源分配时，读 TTL 可能已经到期。

Session 在 FREE 与各 (instance_id, worker_id) 间分配原始逐 key 份额。传输验证原始 generation，以唯一 tag 固定驻留缓冲区，并在完成载荷中记录不可变的原始所有权。完成时使用回执而非当前 Session 元数据，至多释放一次。发布失败先同步再释放；同步失败则保留 pin。 本轮保留上游多 L1 所有者分组与分介质管理器；写入夹具传入显式所有者，模拟时钟迁移到新的 L1 base 模块。不引入另一套回收策略。

这是正确性与生命周期修复，不宣称模型质量、TTFT 或吞吐提升。下文区分本轮 CPU/原生 CUDA 验证与历史阴性对照。

2 · 前后行为对照

原行为 · 失败时序

  1. A 与 B 共享 generation
  2. FREE(A) 减计数
  3. A 完成误释放 B

新行为 · 所有权屏障

  1. 认领原始读份额
  2. 按 tag 固定源内存
  3. 设备完成
  4. 按回执释放一次

3 · 端到端责任流程

  1. Session保存原始逐 key 计数，在 FREE 和 worker 认领间划分。
  2. StorageManager / L1Manager验证原始代次、路由所有者并阻止正常回收释放缓冲区。
  3. Transfer module以不可变的所有者/key/代次分组和唯一 tag 提交拷贝。
  4. Completion handler即使 Session 元数据消失，也释放原 tag；不能消耗更新代次。

编号描述协议要求的先后关系，不表示跨主机串行执行；失败处理与保证边界见下文。
