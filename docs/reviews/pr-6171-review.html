[Bugfix][MP] Pin L2 STORE sources until terminal completion

An admitted L2 write keeps reading its L1 source after a read lease can expire. Each adapter task owns its source pin until terminal completion, including during shutdown.

1 · Problem, behavior and boundaries

Previous behavior

StoreController held TTL read reservations, then released outstanding reservations during stop. A slow asynchronous adapter could continue reading after TTL expiry or after shutdown cleanup allowed source reuse. Bigtable could also report one preparation failure while sibling executor readers still ran.

Behavior at this head

The controller reserves original generations, pins each admitted task under a process-unique tag, and releases only after the adapter reports a terminal result. stop closes admission and drains admitted tasks before adapters or L1 close. Bigtable waits for every preparation reader before surfacing failure.

Builds on #6067 and #5478 source ownership. #5673 covers LOAD destinations; #6175 covers process fencing. This PR’s additional responsibility is L2 STORE source lifetime and shutdown drain.

2 · End-to-end implementation walkthrough

  1. StorePolicy selects target adapters. For each target, StoreController deduplicates keys, reserves reads with generation capture, and calls pin_read_buffers using a unique l2-store tag. Only successfully pinned objects are submitted.
  2. A failed pin releases only its original matching generation. A rejected submission calls finish_read_transfer for that task’s tag; it cannot release a sibling replica’s admitted pin.
  3. InFlightStoreTask retains keys and transfer_tag. Both successful and failed pop_completed_store_tasks results are terminal buffer-lifetime fences. Finalization releases that tag, then applies policy-controlled L1 deletion.
  4. stop sets the stop flag under the adapter-operation queue lock and closes StoreListener admission. Later L1 callbacks are ignored under its lock, including after the notifier closes. The loop keeps polling admitted tasks and applies previously accepted adapter operations before exit.
  5. New runtime adapter add/remove requests are rejected once stopping begins. StorageManager’s existing close order stops controllers before adapters and L1. Adapters must remain alive and publish terminal results throughout the drain.
  6. The adapter interface now states that a submit exception leaves no access to caller buffers, and returned task results mean all reads ended. Bigtable gathers preparation results with return_exceptions=True so a failed sibling does not bypass other source readers.
  7. pin_read_buffers validates the original generation while holding the L1 manager mutex. A unique transfer tag prevents ordinary deletion, eviction, clear and temporary-object cleanup from reclaiming the source until finish_read_transfer.

3 · Alternatives and responsibility boundaries

  • Increasing TTL cannot bound real storage latency. Releasing pins on a controller timeout is unsafe unless a backend fence proves reads stopped. Copying all sources into private staging buffers would change memory cost and ownership; this patch reuses the existing read-pin interface.

5 · Risks and focused review questions

  • A stalled adapter can block stop indefinitely. This is deliberate source-lifetime preservation; bounded shutdown requires a separately validated operation-cancellation or process-isolation fence.
  • The controller cannot repair an adapter that admits work and raises without an ID, or publishes terminal completion too early. Native partial admission, external cancellation, SDK/RDMA teardown and serde-owned staging are outside this proof.
  • Explicit force deletion and externally closing adapters or L1 during I/O remain unsupported. Bigtable tests use a fake cloud service; no live cloud, serving throughput or accuracy result is claimed.

Suggested review order

  1. Read the source-ownership and terminal adapter contract, then trace reserve → pin → submit → terminal result.
  2. Trace shutdown admission locks, accepted adapter operations and the existing StorageManager close order.
  3. Review gated multi-adapter, expiry, rejection, terminal failure and Bigtable sibling-reader tests.

1 · 问题、行为与边界

原有行为

StoreController 原先只持有 TTL 读取预留，并在 stop 时释放未完成预留。慢异步适配器可能在 TTL 到期或关闭清理允许源复用后继续读取。Bigtable 也可能在一个准备任务失败时报告完成，而兄弟 executor 任务仍在读取。

此 head 的行为

控制器预留原始代次，用进程唯一标签 pin 每个接纳任务，只在适配器报告终态结果后释放。stop 关闭准入并排空已接纳任务，然后才能关闭适配器或 L1。Bigtable 等待所有准备读取结束后再报告失败。

基于 #6067 与 #5478 的源所有权。#5673 处理 LOAD 目标，#6175 处理进程屏障。本 PR 新增 L2 STORE 源生命周期与关闭排空责任。

2 · 端到端实现讲解

  1. StorePolicy 选择目标适配器。StoreController 为每个目标去重键、预留并捕获读取代次，再使用唯一 l2-store 标签调用 pin_read_buffers。只提交成功 pin 的对象。
  2. pin 失败时只释放自身匹配的原始代次。提交被拒时，对该任务标签调用 finish_read_transfer；不会释放其他已接纳副本的 pin。
  3. InFlightStoreTask 保存键与 transfer_tag。pop_completed_store_tasks 的成功和失败结果都必须是源缓冲生命周期终态屏障。结算先释放该标签，再按策略删除 L1 对象。
  4. stop 在适配器操作队列锁内设置停止标志，并关闭 StoreListener 准入。后续 L1 回调在其锁内被忽略，notifier 关闭后也一样。循环继续轮询已接纳任务，并在退出前处理之前接纳的适配器操作。
  5. 开始停止后拒绝新的运行时适配器增删请求。StorageManager 既有关闭顺序先停控制器，再关适配器和 L1。排空期间适配器必须保持存活并发布终态结果。
  6. 适配器接口明确：提交抛错后不能仍访问调用者缓冲；返回任务结果表示全部读取已结束。Bigtable 用 return_exceptions=True 收集准备结果，避免一个任务失败时绕过其他仍读取源的任务。
  7. pin_read_buffers 在 L1 管理器互斥锁内校验原始代次。唯一传输标签阻止普通删除、驱逐、清空和临时对象回收；finish_read_transfer 才解除对源缓冲区的保护。

3 · 替代方案与责任边界

  • 增大 TTL 无法约束真实存储时延。除非后端屏障能证明读取已停止，控制器超时后释放 pin 就不安全。把所有源复制到私有 staging 会改变内存成本和所有权；本补丁复用既有读取 pin 接口。

5 · 风险与聚焦审阅问题

  • 适配器卡住可能使 stop 无限等待。这是有意保持源生命周期；有界关闭需要另行验证的操作取消或进程隔离屏障。
  • 控制器无法修复已接纳工作却不返回 ID 就抛错，或提前报告终态的适配器。原生部分接纳、外部取消、SDK/RDMA 关闭及 serde 自有 staging 不在本证明范围。
  • 活动 I/O 期间不支持强制删除或外部关闭适配器/L1。Bigtable 测试使用假云服务，未证明真实云端、服务吞吐或准确率结果。

建议审阅顺序

  1. 先读源所有权与适配器终态契约，再跟踪预留 → pin → 提交 → 终态结果。
  2. 跟踪关闭准入锁、已接纳适配器操作与既有 StorageManager 关闭顺序。
  3. 检查受控多适配器、租约到期、提交拒绝、终态失败与 Bigtable 兄弟读取测试。
