Cached block IDs in the vLLM MP connector

dev a4a688827def → 528fb9fd8108

The MP scheduler must append incremental block IDs exactly once. A legacy scheduler can also send a resumed request in the cached list with a complete allocation.

Scheduler handoff

  1. vLLM builds SchedulerOutput
  2. LMCache builds step metadata
  3. Request tracker appends the block delta

Two representations of a resumed request

Step inputOwnership of block IDsTracker action
Current cached stepIncremental IDsAppend the supplied IDs
Legacy cached step with an unflagged IDIncremental IDsAppend the supplied IDs
Legacy cached step with a flagged IDComplete allocation already recordedKeep the recorded IDs

Code and tests

The former direct field access raised AttributeError on the first nonempty cached step in the new format. Read the optional legacy membership set once per batch. MRV2 readmits a resumed request through scheduled_new_reqs with its full allocation. In earlier vLLM the MRV2 path already moved resumed requests into that list before building cached data. The scheduler still reports actual preemption events using preempted_req_ids. The transfer and flush methods retain their existing behavior.

Review the tracker block list after each representation. Extending the existing consumer test keeps its no-store assertions and supplies nonempty blocks. Treating every legacy cached row as incremental would duplicate a full allocation. The production hunk is three added lines and one replacement in a single MP method.

Validation

The original LMCache dev connector failed the new current-format case. A separate check using the actual vLLM CachedRequestData class raised the same AttributeError. Applying this diff gave 22 passing tests in the changed module and 4 passing integration probes in the same runtime. Ruff lint, format and git diff --check passed. The H20 image backport ran GLM-5.3-Flash with a separate LMCache process and recovered 3,840 external cache tokens across a vLLM restart, with 0 GPU prefix hits and the correct answer. This run used the delivery image with its other patches. Multi-node stress and a forced live eviction were outside this PR test.

MP 调度器需要把增量块 ID 追加一次。旧调度格式还能在缓存请求列表中携带已恢复请求和它的完整块分配。

调度数据传递

  1. vLLM 生成 SchedulerOutput
  2. LMCache 构建本步传输元数据
  3. 请求跟踪器追加本步新增的块

调度器如何表示恢复请求

本步输入块列表语义跟踪器动作
新版缓存请求增量块 ID追加给定块
旧版缓存请求，ID 未标为恢复增量块 ID追加给定块
旧版缓存请求，ID 标为恢复完整分配已登记保留已登记的块

改动及测试

原有代码直接读取旧字段，在新版首次处理非空缓存请求列表时触发 AttributeError。修复在每批开始时读取一次可选的旧版恢复 ID 集合。MRV2 会通过 scheduled_new_reqs 重发恢复请求和完整分配。之前的 vLLM 在生成缓存请求数据前也会把 MRV2 的恢复请求移入该列表。调度器继续使用 preempted_req_ids 表示本步发生的抢占，既有传输和刷写逻辑继续生效。

检查三种输入处理后的块列表。测试扩展既有消费端用例，保留零写入断言，并给出非空块 ID。如果无条件对每种旧请求追加，恢复时会重复登记整组块。运行时代码只修改一个 MP 方法。

验证记录

LMCache dev 原始实现未通过新版格式用例。另一次验证使用 vLLM 的真实 CachedRequestData 类型，得到相同 AttributeError。应用改动后，原测试模块 22 项以及额外集成验证 4 项通过。Ruff 静态检查、格式检查和 git diff --check 通过。H20 交付镜像回移这项修复后，GLM-5.3-Flash 使用独立 LMCache 服务，重启 vLLM 后从外部 L1 取回 3,840 个 token，GPU 前缀命中为零，答案正确。该模型验收还包含交付镜像的其他补丁。本 PR 的验证范围未覆盖多节点压力和实机强制驱逐。
