[Bugfix][MP] Order replacement lookups and session end after RPC acknowledgements

Local completion is not a remote-handler fence. Preserve admitted LOOKUP, status and FREE acknowledgements until replacement or END can safely follow them.

1 · Problem, behavior and boundaries

Previous behavior

Previously, cleanup could forget in-flight RPCs, and end_session could wait only for currently tracked LOOKUP/status work. A tail FREE or an explicit FREE could still be executing when END removed the session. A late handler could recreate state or act on replacement metadata.

Behavior at this head

LookupState now transfers unconfirmed or failed raw futures exactly once. The scheduler adapter retains cleanup obligations and tracks explicit FREE futures. Each server independently submits END only after all its predecessors succeed. Replacement LOOKUPs are retried by scheduler ticks after the same acknowledgement fence.

Refs #5578; overlaps in call ordering with #5579 and missing FREE submission with #5657 are distinct from retaining successful handler acknowledgements. #6100 handles abandoned backend jobs. This PR does not include server buffer pins.

2 · End-to-end implementation walkthrough

  1. LookupState.submit checks final state under its lock, admits LOOKUP and records its future before callbacks can run. Status and unequal-hit tail FREE futures join the same acknowledgement set.
  2. close_and_take_pending_rpcs stops new sends and moves pending/failed obligations to the caller once. A local deadline cannot cancel a remote handler, and a failed future is retained as evidence of an unknown remote outcome.
  3. cleanup_lookup_result removes the result but keeps per-server futures. free_lookup_locks adds explicit release futures. Both cleanup-before-END and END-before-cleanup therefore preserve the same ordering obligation.
  4. _OrderedSessionEnd registers completion callbacks without waiting on the scheduler thread. A slow server holds back only its own END. Any failed predecessor prevents that server’s END and is logged.
  5. A replacement attempt establishes one deadline using the existing MQ timeout. Pending acknowledgements return False; check_lookup_result returns None until submission is retried. Failure or expiry produces a stable miss and cannot be revived by a late ACK.
  6. Successful predecessors are pruned before checking the deadline. Cleanup or END cancels a deferred replacement. Completion callbacks never launch a cancelled replacement; no completed-request history is retained.

1 · 问题、行为与边界

原有行为

此前 cleanup 可能丢弃仍在执行的 RPC，end_session 只处理当前仍被跟踪的 LOOKUP/状态工作。尾部 FREE 或显式 FREE 可能在 END 删除 session 时仍运行；迟到的处理器可能重新创建状态或操作替换后的元数据。

此 head 的行为

LookupState 现在只转交一次未确认或失败的原始 future。调度适配器保留 cleanup 的排序义务，并跟踪显式 FREE。每个服务器独立地在自身所有前序 RPC 成功后提交 END；替换 LOOKUP 由调度 tick 在同一确认屏障后重试。

关联 #5578；#5579 的调用顺序与 #5657 的漏发 FREE，与本 PR 保留处理器成功确认的范围不同。#6100 处理后端废弃任务。本 PR 不含服务器缓冲区 pin。

2 · 端到端实现讲解

  1. LookupState.submit 在锁内检查最终状态，提交 LOOKUP 并记录 future，再注册可能立即执行的回调。状态查询与各服务器命中不一致时的尾部 FREE 也进入同一确认集合。
  2. close_and_take_pending_rpcs 停止新发送，只把待完成和失败的排序义务转交给调用者一次。本地超时不能取消远端处理器，失败的 future 仍保留，表示远端结果未知。
  3. cleanup_lookup_result 删除结果，但保留各服务器的 future；free_lookup_locks 加入显式释放的 future。因此，无论先 cleanup 还是先 END，排序义务都不会丢失。
  4. _OrderedSessionEnd 注册完成回调而不阻塞调度线程。慢服务器只阻止自己的 END；任一前序 RPC 失败时，该服务器不会发送 END，并记录错误。
  5. 替换尝试沿用 MQ timeout 建立一次性截止时间。确认未完成时提交返回 False；check_lookup_result 在重新尝试提交前返回 None。失败或超时变为稳定 miss，迟到的 ACK 不会使它重新启动。
  6. 检查截止时间前先移除已成功的前序 RPC。cleanup 或 END 取消延后的替换请求；完成回调不会启动已取消的替换，也不保存已完成请求的历史。

5 · 风险与聚焦审阅问题

  • 未增加线协议尝试 ID、任意请求 ID 复用、传输重连协议或后端退休机制。其他客户端复用活动 ID 前也必须遵守同样的顺序。
  • 确认失败时有意不发送 END，这不代表远端清理已成功。连接器仍必须发送正常的一次性 request-finished 通知。
  • 重点检查锁外回调注册、LookupState 锁内的一次性交接，以及延后替换映射仅由调度线程持有。这里未测量模型输出或吞吐收益。

建议审阅顺序

  1. 先读 lookup-state 设计契约，再检查 future 记录与 close_and_take_pending_rpcs。
  2. 沿连接器 cleanup、显式 FREE、替换提交和 END 跟踪到适配器。
  3. 先检查延迟/失败前序 RPC 测试和真实 RPC 补充检查，再检查截止时间案例。
